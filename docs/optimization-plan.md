# m-typora 优化方案

> 状态：草案 · 2026-10-29
>
> 一句话定位：**免费、开源、不丢数据的 Typora。** 打开就写，写完就走。

## 1. 背景

到 v0.1 为止，m-typora 的投入集中在“像 Typora”：排版逐项实测还原、扩展语法、保存时内容原样往返。这部分已经做得很扎实。

但以日常写作工具的标准看，还缺两样东西：

1. **可靠**：编辑器只在用户主动保存时写盘，崩溃、外部修改、同步盘冲突都可能让内容丢失。
2. **顺手**：文件夹只能看不能管，启动时不会回到上次在写的文件，新建一篇笔记要走完整的“另存为”流程。

本方案只补这两样，不改变“轻量编辑器”的定位。

## 2. 设计原则

每个新功能在动手前都要过这三条，过不了就不做：

1. **文件永远是普通的 `.md`。** 不引入数据库、工作区配置文件、私有语法；用户随时可以换回别的编辑器。应用自己的数据（草稿、历史版本）只放在用户数据目录。
2. **不用的人感觉不到它。** 不新增常驻面板，不新增概念；功能藏在菜单、右键菜单或出事时才出现的提示条里。
3. **默认值就是对的。** 优先改进默认行为，而不是增加开关。

## 3. 不做的事

明确排除，避免范围蔓延：

- 双链 `[[ ]]`、反向链接、标签系统、关系图谱、每日笔记
- 插件系统
- 标签页（保持一个窗口一个文档）
- 自建云同步、账号体系、移动端
- 全文搜索索引（现有的实时搜索对轻量使用足够）
- 本轮不做：复制到公众号 / 知乎、中英文排版增强、导出长图和 Word、代码签名与自动更新

## 4. 路线图总览

| 版本 | 主题 | 内容 | 预估 |
|---|---|---|---|
| v0.2 | 不丢数据 | 原子写入、草稿与崩溃恢复、外部修改检测、自动保存默认开启、本地历史版本、同一文件只开一个窗口 | 2–3 周 |
| v0.3 | 顺手 | 侧边栏文件操作、恢复上次的文件、在当前文件夹新建、大文档性能、拼写检查开关 | 2 周 |

预估按一个人业余时间开发、包含端到端测试计算。工作量标记：**S** ≤ 1 天，**M** 2–3 天，**L** ≥ 1 周。

## 5. v0.2：不丢数据

目标：**任何情况下，用户输入过的内容都能找回来。**

### 5.1 原子写入 · S

**现状**：`fs:save-file` 直接 `writeFile` 覆盖目标文件（[src/main/index.ts](../src/main/index.ts) 的 `fs:save-file`）。写到一半时崩溃、断电或磁盘写满，会留下一个被截断的文件，原内容也没了。

**方案**：
- 先写到同目录的临时文件 `.<文件名>.m-typora-tmp`，`fsync` 后 `rename` 覆盖原文件。
- 写之前用 `realpath` 解析符号链接，替换的是链接指向的真实文件，而不是把链接本身换成普通文件。
- 保留原文件的权限位。
- Windows 上目标文件被其他程序占用时 `rename` 会报 `EPERM`：重试 3 次（间隔 100ms），仍失败就报错并保留临时文件。

**验收**：保存后磁盘上没有残留临时文件；模拟写入中途抛错时，原文件内容不变。

### 5.2 草稿与崩溃恢复 · M

**现状**：未保存的内容只存在于渲染进程内存里。“未命名”文档、关闭自动保存时的修改，在崩溃后全部丢失。

**方案**：
- 渲染进程在内容变化后 2 秒（防抖）把草稿发给主进程：`{ id, path, content, baseMtime }`。`id` 是窗口创建时生成的随机值。
- 主进程写到 `userData/drafts/<id>.json`（同样原子写入）。
- 正常保存、选择“不保存”关闭、或内容回到与磁盘一致时，删除该草稿。
- 启动时主进程检查 `drafts/`：
  - 有残留草稿就为每份草稿打开一个窗口，顶部显示提示条：**“上次未保存的内容已恢复”**，按钮为 **保存** / **丢弃**。
  - 对于已有路径的草稿，如果磁盘文件在 `baseMtime` 之后被改过，提示条改为说明冲突，并提供 **另存为副本**。
- 草稿只保留 30 天，启动时清理过期的。

**验收**：编辑未命名文档后强制结束进程（`kill -9`），重启时内容恢复；正常保存并退出后 `drafts/` 为空。

### 5.3 外部修改检测 · M

**现状**：主进程不监听文件变化。用户把笔记放在 iCloud / Dropbox / 坚果云或 git 仓库里时，外部的修改不会反映到编辑器；此时一保存，就用旧内容覆盖了外部修改。这是目前最大的数据丢失隐患。

**方案**：

*当前文件*
- 主进程用 `fs.watch` 监听**文件所在的目录**并按文件名过滤（很多编辑器和同步工具用“写临时文件再改名”的方式保存，只监听文件本身会丢事件），事件防抖 300ms。
- 收到变化后读取内容，与“最后一次已知的磁盘内容”比较；相同就忽略。这一步同时过滤掉自己保存触发的事件。
- 编辑器**没有**未保存修改：静默重新载入，保持滚动位置和光标所在的段落。
- 编辑器**有**未保存修改：顶部提示条 **“文件已在外部修改”**，按钮为 **载入外部版本** / **保留我的版本**（选后者时，下次保存会覆盖外部版本，并先把外部版本存进本地历史，见 5.5）。
- 文件被删除或移走：提示条 **“文件已被删除或移动”**，文档标为未保存，保存时走另存为。

*保存前兜底*
- 网络盘等场景下 `fs.watch` 可能收不到事件。保存前再 `stat` 一次：如果磁盘的修改时间晚于上次读取或保存，就按上面“有未保存修改”的情况处理，而不是直接覆盖。

*侧边栏*
- 对打开的文件夹做递归监听（Electron 45 自带的 Node 在三个平台上都支持 `recursive`），防抖 500ms 后刷新文件树，替代现在“保存后手动刷新”的做法。

**验收**：在终端里 `echo` 追加内容到已打开且无修改的文件，编辑器 1 秒内更新；有未保存修改时出现提示条，两个按钮的结果都符合描述；外部修改后直接 `⌘S` 不会覆盖。

### 5.4 自动保存默认开启 · S

**现状**：`autoSave` 默认为 `false`（[src/renderer/src/prefs.ts](../src/renderer/src/prefs.ts)），且只对已保存过的文件生效。

**方案**：
- 新用户默认开启。已有用户的偏好原样保留：偏好在打开文件夹、保存文件等操作时会整份写入 `localStorage`，几乎所有已有用户都已存下了 `autoSave: false`，修改默认值不会影响他们。
- 未命名文档仍然不自动保存（不能替用户决定存到哪里），由 5.2 的草稿兜底。
- 切换窗口、关闭窗口、退出应用时，如果开启了自动保存且有修改，立即保存，不等防抖。

### 5.5 本地历史版本 · M

**方案**：
- 每次保存**之前**，把磁盘上的旧版本复制到 `userData/history/<路径哈希>/<时间戳>.md`。距上一份快照不足 10 分钟时跳过，避免自动保存产生大量快照，同时保证一段编辑开始前的原始版本一定被保留。
- 磁盘上的版本来自外部（不是本窗口读到或写入的内容）时，不受 10 分钟限制，一律保留：它可能在别处没有副本。
- 每个文件最多保留 50 份，超过 30 天的清理掉。总占用超过 200MB 时从最旧的开始删。
- 入口：**文件 › 历史版本…**（以及标题栏下拉菜单）。打开一个对话框，左边是时间列表，右边是该版本的原文预览，按钮为 **恢复此版本**（恢复后作为一次普通修改，可以撤销）和 **在访达中显示**。
- 文件改名后历史跟着走：重命名时把目录一起迁移。

**验收**：连续保存三次（间隔超过 10 分钟，测试里用可注入的时钟），历史中出现三份；恢复后内容一致且可以 `⌘Z` 撤销。

### 5.6 同一文件只开一个窗口 · S

**现状**：同一个文件可以在两个窗口里同时打开，互相覆盖。Windows / Linux 上没有单实例锁，在资源管理器里双击 `.md` 会再启动一个进程。

**方案**：
- 主进程维护 `路径 → 窗口` 的映射，数据来源是现有的 `window:set-title` 消息（已经带上了路径）。
- 任何窗口要打开的文件如果已在别的窗口里打开，直接聚焦那个窗口。
- 调用 `app.requestSingleInstanceLock()`，在 `second-instance` 事件里解析命令行参数，交给同一套打开逻辑。

## 6. v0.3：顺手

目标：**以文件夹为单位写作时，不需要切到访达。**

### 6.1 侧边栏文件操作 · M

**现状**：侧边栏的文件树和文档列表只能点开文件，没有右键菜单。

**方案**：
- 右键菜单（文件）：**新建文件**、**新建文件夹**、**重命名**、**移到废纸篓**、**在访达中显示**、**复制路径**。
- 右键菜单（空白处或文件夹）：**新建文件**、**新建文件夹**、**在访达中显示**。
- 删除一律用 `shell.trashItem` 移到废纸篓，不做永久删除；删除的是当前打开的文件时，按 5.3 中“文件已被删除”的情况处理。
- 重命名的是当前打开的文件时，更新编辑器里的路径和标题。
- 不做拖拽移动（容易误操作，收益有限）。

**注意**：`readTree` 目前会隐藏不含 Markdown 文件的文件夹（[src/main/files.ts](../src/main/files.ts)），刚新建的空文件夹会“消失”。要改成显示空文件夹，但继续隐藏只含非 Markdown 文件的文件夹。

### 6.2 恢复上次的文件 · S

**现状**：启动时会恢复上次的文件夹（`lastFolder`），但编辑区总是空白的未命名文档。

**方案**：
- 不带文件参数启动时，重新打开上次关闭的文件（文件不存在就跳过）。
- 记住最近 50 个文件各自的滚动位置和光标位置，重新打开时恢复。
- 有草稿要恢复（5.2）时，以草稿为准。

### 6.3 在当前文件夹新建 · S

**现状**：新建 → 写 → `⌘S` → 在对话框里选目录、起名，一共四步。

**方案**：
- 打开了文件夹时，侧边栏顶部加一个 **+** 按钮，`⌘N` 的行为也改为：在当前文件夹（选中的是子文件夹时就在子文件夹里）直接创建 `未命名.md`（重名时依次为 `未命名 2.md`……），打开它，并让标题栏进入重命名状态。
- 没有打开文件夹时，`⌘N` 保持现有行为。
- 不做“按第一行标题自动命名”：会让文件名在用户不知情时变化，与原则 2 相悖。

### 6.4 大文档性能 · M

**现状**：每次按键都会把整篇文档序列化成 Markdown，用来判断是否有修改（`onContentChange` → `currentMarkdown()`，见 [src/renderer/src/app.ts](../src/renderer/src/app.ts)）。文档越长，打字越卡。打开文件夹时，`readTree` 会逐个读取每个文件的开头来生成摘要，文件多时很慢。

**方案**：
1. **先建立基准**：在 `samples/` 下用脚本生成 1 万行和 5 万行的文档，以及一个含 2000 个文件的文件夹；在端到端测试框架里记录下面“指标”一节中的数字。
2. 修改检测改为：按键时只看 ProseMirror 事务的 `docChanged` 标出“可能有修改”，在空闲时（`requestIdleCallback`，最长 500ms）再序列化比较，处理“改了又撤销回原样”的情况。
3. 字数统计、大纲等派生信息已有 150ms 防抖，确认它们不在每次按键时触发全量计算。
4. `readTree` 并发读取（限制 16 个并发），并按 `mtime` 缓存摘要，文件没变就不重新读。

**指标**（在一台 M1 机器上测量，写入 `docs/test-plan.md`）：
- 1 万行文档：按键到画面更新 p95 < 16ms
- 打开 1 万行文档：< 1s
- 冷启动到可以输入：< 1.5s
- 2000 个文件的文件夹首次加载：< 1s

### 6.5 拼写检查开关 · S

**现状**：`spellcheck: false` 写死在窗口配置里（[src/main/index.ts](../src/main/index.ts)）。

**方案**：偏好设置 › 编辑器 增加 **拼写检查**，默认关闭；macOS 使用系统拼写服务，Windows / Linux 使用 Chromium 内置的英文词典。代码块、行内代码、公式不做检查。

## 7. 测试

沿用现有的端到端测试框架（`npm run test:e2e`），在 [docs/test-plan.md](test-plan.md) 中按版本新增章节：

- **S. 数据安全**（v0.2）：原子写入、崩溃恢复（强制结束进程后重启）、外部修改的三种情况、保存前兜底、历史版本、同一文件只开一个窗口
- **T. 文件夹与启动**（v0.3）：侧边栏右键操作、空文件夹显示、恢复上次文件与光标、在当前文件夹新建
- **U. 性能基准**（v0.3）：6.4 中的四项指标，超出阈值时测试失败

## 8. 风险

| 风险 | 应对 |
|---|---|
| `fs.watch` 在网络盘、部分同步盘上不可靠 | 保存前的 `stat` 兜底（5.3）保证至少不会静默覆盖 |
| 同步工具频繁改写文件导致反复重新载入 | 内容比较 + 防抖；内容没变就不重新载入 |
| 草稿和历史版本占用磁盘 | 数量、时间、总量三重上限（5.2、5.5） |
| 静默重新载入打断正在阅读的用户 | 只在没有未保存修改时静默载入，并保持滚动位置 |
